# CLAUDE.md — mcp-context-server

## Que es este proyecto

Servidor MCP que actua como memoria inteligente de proyectos para Claude Code. Indexa codebases, responde queries con contexto relevante comprimido, y registra metricas de uso. El objetivo es reducir el consumo de tokens en Claude Code usando DeepSeek Flash como preprocesador barato en lugar de mandar archivos completos al contexto.

## Hardware donde corre

- **openclaw-server**: PC de casa, i7 3ra gen, 16GB DDR3, sin GPU, ethernet fija, UPS
- Todo el procesamiento de IA va por API (DeepSeek), ningun modelo corre local
- Embeddings con `all-MiniLM-L6-v2` en CPU — es liviano, no requiere GPU
- Acceso remoto via Tailscale

## Clientes que se conectan

- Laptop principal
- Kali Linux en SSD portable (mismo entorno en cualquier maquina donde se conecte)

## Stack

### Backend (server/)
- Python 3.11+ (probado en 3.13 con Kali)
- `mcp` SDK — protocolo MCP stdio
- `anthropic` SDK con `base_url` de DeepSeek — para comprimir contexto
- `sentence-transformers` (all-MiniLM-L6-v2) — embeddings en CPU
- `chromadb>=1.0` con PersistentClient — vector store local en disco
- `gitpython` — clonar repos desde GitHub
- `psycopg2` — conexion a PostgreSQL en Railway

### Infraestructura
- PostgreSQL en Railway
- Tailscale para acceso remoto seguro
- systemd para correr el MCP Server como servicio
- `claude mcp add --scope user` para registrar el servidor en Claude Code

## Decisiones de diseno importantes

- **ChromaDB usa PersistentClient** apuntando a `CHROMA_PERSIST_PATH`. Nunca usar `chromadb.Client()` en memoria — el indice se pierde al reiniciar.
- **No modelos locales**. El hardware no tiene GPU. Todo AI va por API de DeepSeek.
- **El MCP solo escribe en `PROJECTS_BASE_PATH`** al clonar repos. Nunca modifica archivos de proyectos existentes.
- **La whitelist se carga dinamicamente desde PostgreSQL** al iniciar el servidor, no es solo hardcodeada en env.
- **`clone_project` = clonar + indexar en un solo paso**. No hay flujo separado.
- **GitHub token** en env para repos privados. Funciona tambien para repos publicos.
- **La tabla `token_usage` no existe** — los tokens se registran directamente en la tabla `queries` para evitar duplicacion.
- **`index_project` solo recibe el nombre del proyecto**, no el path — lo busca en la base de datos.
- **`CLAUDE.md` esta en BLOCKED_FILENAMES** — excluido del indice para que no contamine las busquedas semanticas.
- **`from __future__ import annotations`** es obligatorio en todos los modulos Python. En Python 3.13 + ChromaDB 1.x, `PersistentClient` es una funcion y `function | None` falla en runtime sin este import.
- **Virtualenv en `server/.venv/`** — Kali Linux bloquea pip global por PEP 668. Siempre usar `.venv/bin/python` y `.venv/bin/pip`.
- **Re-indexado limpio**: `index_project` borra los chunks anteriores con `collection.delete(where={"project_id": ...})` antes de re-indexar.
- **Queries cross-repo**: ChromaDB filtra con `{"project_id": {"$in": [...]}}` cuando se pasan multiples proyectos.
- **ChromaDB rechaza múltiples campos directos en `where`**: cuando se filtra por más de un campo (ej. `project_id` + `file_path`), hay que usar `{"$and": [{"project_id": {"$eq": ...}}, {"file_path": {"$eq": ...}}]}`. Un dict plano con dos claves falla en ChromaDB 1.x con "Expected where to have exactly one operator". Afecta a `get_file_chunks()` en `retriever.py`.
- **Umbral de distancia**: `MAX_DISTANCE=1.2` (env configurable) — filtra chunks con cosine distance > 1.2. Con `all-MiniLM-L6-v2`, queries NL contra codigo dan 0.6-1.1; valores < 1.0 filtran demasiado y devuelven contexto vacio.
- **Delta indexing**: `index_project(incremental=True)` usa hash MD5 por archivo; solo re-indexa archivos cambiados, borra chunks de archivos eliminados.
- **IDs de chunks deterministicos**: SHA1 de `"{project_id}:{rel_path}:{chunk_index}"` — permite delete preciso por archivo en modo incremental.
- **Grafo de imports**: durante el indexado se extraen imports de Python (ast) y JS/TS (regex) y se guardan en `file_imports`. `find_usages` consulta esta tabla.
- **audit_project autodetecta el tipo de proyecto**: cuenta extensiones `.tsx/.jsx` vs `.py/.java/.go/.rs/.cs` en `indexed_files` via `db.get_file_extensions()`. Si hay mas TSX/JSX usa `FRONTEND_QUERIES` (correctness, accessibility, performance, state_management, seo, component_design, error_handling, deprecated, tests, bundle_size, hydration, theming, over-engineering); si no, `BACKEND_QUERIES` (correctness, security, error_handling, code_quality, deprecated, config_secrets, imports, io_operations, tests, over-engineering). Con `categories` explicitas mezcla ambos sets.
- **Categoria `correctness` (cazabugs)**: es la unica que busca bugs de logica reales, no ejes de buenas practicas. Su `prompt_hint` (`_CORRECTNESS_HINT`) lista anti-patrones concretos (update parcial que ignora null, etiqueta/conteo que no coincide con el valor calculado, condicion invertida, is/==, off-by-one). La busqueda semantica engancha mal estos bugs (matchea comentarios antes que un `if x is not None`), por eso su estrategia suma barrido estructural de `routers/routes/controllers/api/services/pages/views/hooks`. Sin esta categoria, el audit clasico (solo ejes de calidad) no detectaba bugs como un `if data.notas is not None` que impide limpiar un campo.
- **Categoria `over-engineering` (anti-complejidad)**: el inverso de `correctness` — no caza bugs, caza complejidad innecesaria que igual FUNCIONA (abstraccion prematura con 1 sola impl, dependencia evitable que la stdlib ya cubre, reinvencion de stdlib, boilerplate). Es el ojo del modo ponytail (dev senior perezoso) trasladado al auditor: un hallazgo = un punto donde el codigo bajo mas peldaños de los necesarios en la escalera (YAGNI > stdlib > feature nativa > dep instalada > una linea). Comun a backend y frontend (misma entrada en ambos sets con `_OVER_ENGINEERING_QUERY` identica para no colisionar al hacer `{**back, **front}`). Decisiones clave: (1) **no es una `query` por señal** — el spec original listaba 8 queries, pero el modelo del repo es 1 query semantica + 1 `prompt_hint`; las señales y el guardarrail viven juntos en `_OVER_ENGINEERING_HINT`. (2) **El guardarrail es lo critico**: el hint cierra prohibiendo marcar validacion de input en limites de confianza, manejo de errores anti-perdida-de-datos, seguridad, accesibilidad, concurrencia necesaria (locks/transacciones), reintentos por red/hardware y tests; ante la duda, falso negativo. (3) **No duplica `correctness`**: si es un bug va alli; aqui solo lo que funciona pero se puede borrar. (4) `structural_patterns=["%requirements.txt","%package.json"]` porque la señal "dependencia evitable" es invisible para la busqueda semantica de abstracciones (hay que leer el manifiesto). (5) Severidades en español (ALTO/MEDIO/BAJO) para que `_consolidate` las cuente; rara vez CRITICO. (6) Los campos `ladder_rung`/`simplification` del spec NO se modelan como campos estructurados (romperian `_SEV_RE`): van como texto dentro del `Fix:`.
- **Hints frontend destilados de skills externas (`_PERFORMANCE_HINT`, `_STATE_MANAGEMENT_HINT`, `_ERROR_HANDLING_HINT`, accessibility enriquecido, bloque React en `_CORRECTNESS_HINT`)**: las categorias frontend `performance`, `state_management` y `error_handling` corrian SIN `prompt_hint` (solo query semantica), muy por detras de las de backend. Se hornearon como señales las reglas de las skills de Claude Code **Vercel React Best Practices** (70 reglas: waterfalls/Promise.all, componente definido dentro de otro, estado derivado en useEffect, deps no primitivas, listas sin virtualizar) y **Web Interface Guidelines** (a11y/forms: focus-visible, label/htmlFor, autocomplete/inputmode, prefers-reduced-motion, landmarks, color como unico indicador). Filosofia del usuario que motiva el diseño: **Claude Code usa esas skills para CONSTRUIR; el MCP usa su conocimiento destilado para REVISAR lo ya construido** — misma calidad de revision, muchos menos tokens (una pasada DeepSeek vs arrastrar 70 reglas al contexto). Decisiones: (1) **NO se replica el mecanismo de `web-design-guidelines` (que hace `WebFetch` a una URL en runtime)**: meteria dependencia de red, latencia y un modo de fallo nuevo, y DeepSeek no fetchea igual; las reglas son estables, se hornean fijas. (2) `performance`/`state_management` son frontend-only (no estan en `_BACKEND_MAP`), asi que su hint nuevo no toca al backend. (3) `error_handling` y `correctness` son **compartidas** back/front: sus hints cubren ambos lados con texto autoguardado ("Si el codigo es React/JSX, ademas:" / "En frontend:.../En backend:...") en vez de ramificar por `project_type`, porque `CATEGORY_STRATEGY` se indexa solo por categoria. (4) El guardarrail de `performance` prohibe sugerir useMemo/useCallback/memo para expresiones triviales (sobre-memoizar es su propio coste) — sembrado como `must_not_flag` en el golden set. Casos sembrados nuevos: `fe-fetch-waterfall` + `fe-inline-component` en `fake_frontend/src/pages/Reportes.jsx`, mas el `must_not_flag` `noflag-perf-inline-handler`.
- **Auditoria de contrato cross-repo (`paired_with`)**: cada proyecto se auditaba en aislamiento (`retrieve` filtra por `project_id`), asi que mismatches front<->back eran invisibles. `_contract_audit()` recupera el cliente API del frontend (`api/services`) y los handlers del backend (`routers/routes/controllers`) de AMBOS repos, prefija cada chunk con `[FRONTEND:nombre]`/`[BACKEND:nombre]` en `file_path` para que el modelo distinga, y pide verificar nullability, nombres de campo, tipos y endpoints que no calzan. Capado a `_CONTRACT_MAX_CHUNKS=40` para acotar costo.
- **Recall del audit (`AUDIT_TOP_K=18`)**: el audit recupera 18 chunks por categoria (vs `TOP_K_RESULTS=8` de `query_context`) — prioriza recall sobre costo porque es la via cara y on-demand.
- **Batching del audit (`AUDIT_BATCH_MAX_CHARS`, `deepseek_client._batch_by_chars`)**: `deepseek-chat` tiene ~64K tokens de ventana. Las categorias con `semantic_disabled`/`structural_patterns` sobre `%/components/%`/`%/app/%` (accessibility, theming) cargan TODOS los chunks de esos archivos sin tope; en un repo grande (ej. 190+ componentes) eso supera la ventana y la llamada falla con error 400 — el retry no ayuda (no es transitorio) y cae al `_raw_fallback` que devuelve basura truncada en vez de hallazgos. Por eso `audit_context()` parte los chunks en lotes de `AUDIT_BATCH_MAX_CHARS` (default 120K chars ≈ 30K tokens, midiendo `len(content)` con margen para system+output), audita cada lote en una llamada y **concatena** los hallazgos; un chunk individual que ya exceda el presupuesto va solo en su lote (no se parte: es ≤`CHUNK_SIZE` lineas). Esto mantiene recall completo (se audita todo, en varias pasadas) a cambio de N llamadas. **Las fixtures de 4 archivos nunca tocan este limite — solo se ve a escala real.** `AUDIT_MAX_CHUNKS` (default 0=sin tope) recorta el total de chunks por categoria si se quiere acotar costo; en pruebas se deja en 0. El modo `raw` NO pasa por batching (no llama a DeepSeek) pero SI tiene su propio tope: `AUDIT_RAW_MAX_CHARS` (default 150K chars) acota el TOTAL de la respuesta raw entre todas las categorias — sin el, un repo mediano devolvia 370K+ chars que saturaban el contexto del que llama (caso real con EcuaInventario). El corte es por limite de chunk (nunca a mitad de codigo, via `_raw_fragments_within`) y cada categoria recortada indica cuantos chunks omitio y sugiere pedirse sola con `categories=[...]`.
- **Output estructurado del audit**: `deepseek_client.audit_context()` (distinta de `compress_context()`) antepone `AUDIT_SYSTEM_INSTRUCTIONS` que fuerza formato `**[SEVERIDAD]** archivo:linea — problema. Fix:` y responde `Sin hallazgos.` si no hay nada. Ambas comparten `_call()` (reintentos + fallback a chunks crudos) y `_build_fragments()`.
- **Números de línea por chunk**: el chunking devuelve `(contenido, start_line_1based, end_line_1based)` y guarda `start_line` y `end_line` en metadata de Chroma. `_build_fragments()` numera cada línea del fragmento usando ese `start_line` y cita el rango `(líneas N-M)`, para que el modelo cite `archivo:línea` con precisión real (no inventada). Las funciones de segmento (`_chunk_tsx/_chunk_css/_chunk_python`) devuelven `(offset_0based, lineas)` vía `_segments_from_boundaries()`. **El número de línea NO se embebe en el vector** (sería ruido): se guarda en metadata y se renderiza solo al construir el prompt, así el embedding queda limpio. Índices viejos sin `start_line`/`end_line` siguen funcionando (se omite la numeración / el rango); reindexar (full, no incremental) los repuebla.
- **`query_context` devuelve `locations`**: además del `context` comprimido y `files_referenced`, retorna una lista `locations` con `{file, start_line, end_line, symbols}` (y `project_id` en queries cross-repo) tomada directo de los chunks recuperados, para poder ir a editar sin re-grepear. `list_projects` incluye `path` de cada proyecto (para mapear el cwd a un proyecto indexado).
- **Símbolos por chunk**: `_extract_symbols()` (regex py/js) guarda en metadata los nombres de funciones/clases del chunk (string separado por coma — Chroma solo acepta escalares). Se muestran en el header del fragmento (`— define: foo,bar`) para dar contexto al modelo y son base para un futuro lookup por símbolo.
- **Reranking híbrido (`retriever._rerank`)**: `retrieve()` con `rerank=True` (default, `RERANK_ENABLED`) pide un pool de `top_k × RERANK_CANDIDATE_MULT` candidatos a Chroma y los reordena con `RERANK_W_SEM·semántico + RERANK_W_LEX·léxico`. El score léxico (`_lexical_score`) es la fracción de tokens significativos de la query presentes en el chunk — rescata matches exactos (nombres de símbolo, flags) que el embedding NL→código pierde. Sin deps nuevas; es un mini-híbrido BM25-lite.
- **Consolidación del audit (`_consolidate`)**: tras correr las categorías, parsea de forma determinista (sin coste LLM) los hallazgos `**[SEVERIDAD]**` y ordena CRÍTICO>ALTO>MEDIO>BAJO. Va en `result["summary"]` con `by_severity` y `top`. Evita que un hallazgo crítico quede sepultado bajo ruido de categorías ruidosas (accessibility/theming). **Dedupe ENTRE categorías**: el mismo problema solía salir 2-3 veces con otra redacción (un except silenciado en `security` Y en `error_handling`; API keys en `security` Y `config_secrets` — caso real). Un duplicado es: misma cita `` `archivo:línea` `` (regex `_LOCATION_RE`), o Jaccard de palabras ≥ 0.55 entre detalles. Se ordena por severidad ANTES de dedupear para que sobreviva la copia de mayor severidad. Scan O(n²) asumido: n son decenas de hallazgos.
- **Modo raw del audit (`raw=true`)**: devuelve por categoría los chunks crudos numerados (`_build_fragments`) sin pasar por DeepSeek — coste 0 de LLM, alta fidelidad para que el modelo que llama razone el bug directamente. No genera `summary` (no hay severidades que parsear). Resuelve la tensión "memoria (comprimir) vs auditoría (fidelidad)".
- **Harness de evaluación en 2 capas** (`tests/fixtures/` + `eval/`): para medir recall hace falta ground truth, así que los bugs se SIEMBRAN en fixtures sintéticas (`fake_backend`/`fake_frontend`) y se listan en `expected.json`. **Capa 1** (`tests/test_retrieval_recall.py`): determinista y gratis, indexa en Chroma efímero y verifica que el archivo de cada bug se recupere (mide chunking+embeddings+rerank, sin DeepSeek/Postgres; se salta sin `sentence-transformers`). **Capa 2** (`eval/run_eval.py`): no-determinista, registra+indexa las fixtures, corre el audit completo y puntúa cuántos bugs REPORTA (usa DeepSeek+Postgres, ~centavos, correr a mano). La separación diagnostica: si Capa 1 alta y Capa 2 baja → el problema es el prompt/modelo; si Capa 1 baja → el problema es chunking/embedding. La Capa 2 ademas verifica `expected.json["must_not_flag"]`: codigo que NO debe aparecer en los hallazgos de su categoria (termometro de FALSOS POSITIVOS, no recall). Nace con `over-engineering`, donde marcar de mas (sugerir borrar un lock o una validacion de input externo) es tan grave como no detectar: la corrida falla si hay violaciones, igual que si baja el recall.
- **Estrategias de recuperación por categoría (`CATEGORY_STRATEGY`)**: la búsqueda semántica falla en frontend porque los patrones relevantes están concentrados en archivos concretos, no dispersos. Tres categorías usan recuperación estructural vía `db.get_files_by_path_patterns()` (SQL ILIKE sobre `indexed_files`): `seo` añade siempre `page.tsx`/`layout.tsx` para capturar `export const metadata` y `generateMetadata`; `bundle_size` añade `package.json` completo + primer chunk de cada componente (donde viven los imports); `accessibility` desactiva la búsqueda semántica por completo y carga todos los archivos de `components/`/`app/` para que el modelo busque ausencias (elementos sin aria-label, img sin alt, div con onClick sin role). La función `_dedup()` garantiza que chunks semánticos y estructurales no se dupliquen por `(file_path, chunk_index)`.
- **`db.get_files_by_path_patterns(project_id, patterns)`**: consulta SQL `ILIKE` sobre `indexed_files` para listar archivos por patrón de ruta (ej. `%page.tsx`, `%/components/%`). Usada por la recuperación estructural de `audit_project`.
- **`audit_project` es resiliente por categoría**: cada categoría corre dentro de un `try/except`; si falla (BD, ChromaDB, DeepSeek), el error queda en `report[category].findings` con `exc_info=True` en el log y el resto de categorías sigue ejecutándose.
- **Chunker estructural (TSX/CSS/Python)**: `_chunk_content()` prepend `// {rel_path}` a cada chunk. Para `.tsx/.jsx` divide en limites de componente (`_chunk_tsx`), para `.css/.scss/.sass` en bloques de regla top-level (`_chunk_css`), y para `.py` en defs/clases top-level (`_chunk_python`, via `ast`). `_chunk_python` incluye los **decoradores** en el mismo chunk que su funcion (critico: un endpoint FastAPI `@router.put(...)` debe quedar junto a su handler). Si no se puede parsear o hay <2 definiciones, cae al splitting por lineas. El empaquetado de segmentos (subdividir los > CHUNK_SIZE) esta factorizado en `_pack_segments()`. **Nota**: cambiar la estrategia de chunking solo afecta a archivos re-indexados; los proyectos existentes mantienen chunks viejos hasta un reindex full.
- **El nombre del modelo NO se hardcodea (`DEEPSEEK_MODEL`)**: DeepSeek retira nombres de modelo sin avisar. `deepseek-chat` estuvo hardcodeado en `config.py` hasta el 2026-07-25 y la API llevaba tiempo respondiendo **400** (`supported API model names are deepseek-v4-pro or deepseek-v4-flash`). El problema no fue el 400 sino **como se disfraza**: `_call()` reintenta 3 veces y cae a `_raw_fallback()`, que devuelve chunks crudos y retorna `(texto, 0, 0, 0.0)` **sin propagar el error**. Un `audit_project` asi se ve casi igual a uno limpio (`total_tokens: 0`, `total_cost_usd: 0.0`, `summary.top: []`, `contracts: 0 archivos`); el unico aviso es la linea `[DeepSeek no disponible]` enterrada dentro de cada `findings`. Durante ese periodo **todas** las auditorias y `query_context` devolvieron crudo sin que nadie lo notara. Invariante: si `total_tokens == 0` en un resultado no-`raw`, el LLM no corrio y el reporte no vale. **Ya no hay que deducirlo**: ver el bullet de `RAW_FALLBACK_MARKER`.
- **La respuesta trae bloques `thinking`: nunca leer `content[0].text`**: los modelos v4 de DeepSeek anteponen un bloque de razonamiento, asi que `response.content` llega como `['thinking', 'text']`. El codigo original hacia `response.content[0].text` y reventaba con `AttributeError: 'ThinkingBlock' object has no attribute 'text'` **sobre una respuesta HTTP 200 perfectamente valida**. Como el `except Exception` de `_call()` no distingue causas, eso se reintentaba 3 veces y se reportaba como "DeepSeek no disponible" — un mensaje que mentia sobre lo que pasaba y mandaba a diagnosticar la red o la API key en vez del parseo. Ahora se concatenan solo los bloques `type == "text"` y una respuesta sin ningun bloque de texto lanza `ValueError` con los tipos que si vinieron. Al integrar cualquier modelo nuevo, verificar los tipos de bloque antes de asumir la forma de `content`.
- **Timeout explicito en cliente DeepSeek**: `_get_client()` en `deepseek_client.py` pasa `timeout=DEEPSEEK_TIMEOUT` (default 60s, configurable por env) al constructor de `anthropic.Anthropic`. Sin esto el SDK usa 10 min por defecto, lo que cuelga `query_context`/`audit_project` cuando DeepSeek tarda en responder antes de que entre el retry con backoff.
- **Validacion fail-fast de env vars criticas**: `config.py` define un helper `_require(key)` que lanza `RuntimeError` con mensaje claro si falta `DEEPSEEK_API_KEY`, `DATABASE_URL`, `PROJECTS_BASE_PATH` o `CHROMA_PERSIST_PATH`. Antes se usaba `os.environ["KEY"]` directo, que lanzaba un `KeyError` cripcito al primer uso en runtime, no al arrancar.
- **Doble confirmacion ante drift git (`index_project`)**: antes de indexar, `git_client.check_remote_status()` hace `fetch` y compara local vs remoto. Si el local esta DETRAS del remoto (`behind > 0`) o tiene cambios sin commitear (`dirty`), `index_project` NO indexa: devuelve `{needs_confirmation: true, git_status, warning}`. Para indexar el estado local de todos modos hay que reintentar con `acknowledge_drift=true`. Esto evita el caso real "el local quedo desactualizado respecto a GitHub y se indexo una version vieja". El MCP nunca hace `git pull` automatico (salvo `clone_project` sobre repo ya clonado) — solo avisa y recomienda. El fetch inyecta el token para repos privados; ante fallo de red devuelve `fetch_error` y no bloquea.
- **`EMBEDDING_MODEL` configurable por env**: default `all-MiniLM-L6-v2`. Cambiarlo a un modelo code-aware (`jina-embeddings-v2-base-code`, `nomic-embed-text`) mejora el recall sobre codigo, PERO cambia la dimension del vector e invalida el indice Chroma existente — exige reindex **full** de todos los proyectos. No mezclar modelos en una misma coleccion.
- **Lockfiles y minificados excluidos del indice**: `security.BLOCKED_FILENAMES` incluye los lockfiles (`package-lock.json`, `yarn.lock`, `poetry.lock`, etc.) y `BLOCKED_NAME_SUFFIXES` bloquea `.min.js/.min.css/.bundle.js/.map`. Son autogenerados, enormes y sin valor semantico; antes inflaban el indice y el costo del audit (aparecian en findings de `bundle_size`/`deprecated`).
- **`.gitignore` respetado al indexar (`indexer._git_ignored_paths`)**: ademas de las blocklists de `security`, el indexado consulta a git mismo (`git ls-files --others --ignored --exclude-standard --directory`, via GitPython, solo lectura) que archivos ignora el `.gitignore` del proyecto, y los excluye. Es la fuente de verdad de "archivo generado" de CADA ecosistema sin mantener listas a mano (caso real: se indexaba `ios/Flutter/ephemeral/` y `GeneratedPluginRegistrant.h` de un proyecto Flutter y salian en findings del audit). Funciona con el repo raiz o con repos hijos de primer nivel (directorio padre no-git). Sin repo git no excluye nada extra. Los archivos ya indexados que pasan a ignorados se purgan en el siguiente reindex (en incremental cuentan como eliminados).
- **Drift git en repos hijos (`check_remote_status` + `index_project`)**: si el path del proyecto NO es un repo git, `check_remote_status` busca repos git en los subdirectorios de primer nivel y devuelve `{is_git: false, child_repos: {nombre: status}}` (caso real: EcuaInventario/ registrado como directorio padre con Backend/ y Frontend/ adentro — el drift era invisible). `index_project` agrega los motivos de drift de la raiz Y de cada hijo (behind/dirty por nombre) en el `needs_confirmation`.
- **Verificacion de hallazgos CRITICO/ALTO (`_verify_summary`, `AUDIT_VERIFY_ENABLED` default true)**: segunda pasada DeepSeek (UNA llamada extra por audit) que re-lee el archivo COMPLETO citado por cada hallazgo CRITICO/ALTO del summary (max `_VERIFY_MAX_FINDINGS=12`) y pide veredicto: CONFIRMADO / DESCARTADO / REBAJADO A MEDIO|BAJO. Los descartados salen de `summary.top` y quedan en `summary.descartados` con su motivo (transparencia); los rebajados cambian de severidad; todos llevan `verdict`. Los findings por categoria NO se tocan (el summary es la vista curada; la categoria es el registro crudo). Fail-open en todo: si la llamada falla, el veredicto no parsea o el archivo citado no se resuelve, el hallazgo se CONSERVA — la verificacion nunca borra por error tecnico. Los conteos (`total`/`by_severity`) se ajustan incrementalmente porque `top` esta capado a 25 pero los conteos cubren todo. Motivacion (caso real): el audit de EcuaInventario reporto 3 CRITICOs y los 3 eran falsos; con instrucciones anti-FP + verificacion, la re-corrida dio 0 CRITICOs, 2 ALTOs falsos descartados automaticamente y 1 rebajado, con recall 13/13 y 0/5 falsos positivos en la Capa 2.
- **Guardarrail anti-falsos-positivos del audit (`AUDIT_SYSTEM_INSTRUCTIONS`)**: los chunks son EXTRACTOS, y el modelo reportaba como CRITICO cosas que el resto del archivo desmentia (casos reales: "falta `from datetime import date`" con el import en la linea 4; marcar `F()` bajo `select_for_update` como race condition). Las instrucciones ahora prohiben reportar imports/validaciones/manejo de errores "faltantes" (pueden existir fuera del fragmento), reservan CRITICO para lo demostrable en el propio fragmento, prohiben marcar patrones idiomaticos del framework y prohiben citar `chunk N` (ademas `_build_fragments` ya no anuncia el chunk_index — el modelo lo copiaba como cita `archivo:chunk0`). La categoria `imports` tiene ademas su propio `prompt_hint` que veta "falta import X" / "import no utilizado". Al afinar esto, correr `eval/run_eval.py` (Capa 2) para verificar que el recall no cayo.

- **El token de GitHub NUNCA se persiste en `.git/config` (`git_client`)**: el token se pasa como URL explicita al comando (`repo.git.fetch(url, refspec)` / `repo.git.pull(url)`) y vive solo en memoria durante la llamada. Antes se hacia `origin.set_url(_inject_token(origin.url))`, que (a) escribia un secreto en texto plano en el repo del usuario y (b) al leer la URL ya tokenizada en la llamada siguiente le anteponia otro token via `.git/config` — un bucle que dejaba `https://ghp_x@ghp_x@...@github.com/...` tras 5 indexados y rompia el fetch con "URL rejected: Bad hostname", con lo que la deteccion de drift moria en silencio (todo `index_project` devolvia `fetch_error`). Invariantes: (1) `_inject_token` es **idempotente** — descarta el userinfo previo (`netloc.rsplit("@", 1)[-1]`) y compara el host EXACTO (`github.com` o `*.github.com`, no `"github.com" in netloc`, que mandaba el token a `github.com.atacante.net`). (2) `_clean_persisted_url(origin)` repara en el acto los repos ya corrompidos: si el userinfo parece token (prefijos `ghp_/gho_/ghu_/ghs_/ghr_/github_pat_` o el token actual) lo borra de `.git/config`; un userinfo legitimo (`https://usuario@github.com/...`) se respeta. (3) El fetch pasa refspec explicito `+refs/heads/*:refs/remotes/origin/*` porque `git fetch <url>` a secas solo actualiza `FETCH_HEAD` y dejaria `refs/remotes/origin/*` viejo, **falseando el calculo de behind/ahead**. (4) `clone_from` deja la URL con token escrita: se resetea el origin a la URL limpia justo despues. (5) `_redact()` sobre todo string de error que se devuelva al cliente — git incluye la URL completa en sus mensajes, asi que el token se filtraria al `fetch_error` y de ahi al contexto del modelo. Regresion en `tests/test_git_client.py`.
- **El audit paraleliza por LOTE, no por categoría (`deepseek_client.audit_batches`, `AUDIT_CONCURRENCY`)**: `audit_project` corría 10-13 categorías x N lotes como llamadas HTTP en serie — en un repo grande son minutos, y encima bloqueando el event loop del server MCP (`handle` era `async` pero todo su cuerpo era síncrono). Ahora `handle` va en tres fases: **A)** retrieval de TODAS las categorías, secuencial (Chroma + Postgres + embeddings se quedan en un hilo: son rápidos y así no hay que razonar sobre su thread-safety); **B)** `await asyncio.to_thread(audit_batches, jobs)`, que aplana los lotes de todos los jobs en un único `ThreadPoolExecutor`; **C)** ensamblado y `log_query`, secuencial. La unidad de paralelismo es el lote **a propósito**: repartir por categoría dejaría a `accessibility` (que carga todos los componentes sin tope) marcando sola el tiempo total. La re-agrupación ordena por índice de lote, así que el resultado es idéntico al secuencial. El audit de contrato (`paired_with`) entra en la MISMA pool — por eso `_contract_audit` se partió en `_contract_chunks()` (solo retrieval) + ensamblado en la fase C. `audit_context()` sigue existiendo como atajo de un job para no romper llamadores. La resiliencia por categoría se conserva: fase A envuelve su retrieval en try/except y un fallo de la pool entera marca como error solo los jobs pendientes.
- **`describe_project` separa lo MEDIDO de lo SINTETIZADO**: `facts` sale del índice sin tocar el LLM (dependencias parseadas de los manifiestos, paleta contada con regex sobre CSS/tailwind, fan-in desde `file_imports`, carpetas y convención de nombres) y `guide` es una pasada DeepSeek que EXPLICA los patrones. La paleta y el grafo **no se le preguntan al modelo**: preguntárselos solo agrega colores inventados y módulos que no existen, cuando contarlos es trivial y exacto. Decisiones: (1) el cache (`project_profiles`) es **por dispositivo** y se sella con el `device_indexed_at` con el que se generó — el perfil describe el Chroma local, que es de cada equipo, y se vence solo al reindexar aquí (mismo razonamiento que `device_paths`). (2) Los perfiles con `focus` NO se cachean: son a medida y pisarían el general. (3) Un perfil con `tokens_used == 0` sale con `llm_available: false` y un `warning` explícito, porque `guide` serían los chunks crudos del `_raw_fallback` disfrazados de síntesis (los `facts` siguen valiendo). (4) El muestreo excluye `tests/`, `fixtures/` y `__mocks__/`: imitan otro sistema a propósito y no representan las convenciones del repo — caso real, en ESTE repo `tests/fixtures/fake_backend/routers/` se llevaba todo el muestreo. (5) `_parse_manifest` descarta el header `// ruta` que el chunker antepone: rompía `json.loads` del `package.json` y colaba una dependencia llamada `//`.
- **`check_updates` distingue dos ejes de "viejo" que se confundían**: el REPO puede estar detrás de GitHub (necesita `git pull`, se detecta con fetch) y el ÍNDICE puede estar detrás del repo (necesita `index_project`, se detecta sin red comparando `device_indexed_at` con la fecha del último commit). `check_remote_status` ya sabía lo primero pero solo se usaba como gate dentro de `index_project`. Los fetch van en paralelo con `asyncio.to_thread` + `gather` (en serie sobre decenas de proyectos la tool sería inusable). **Matiz del invariante "el MCP nunca hace git pull automático"**: sigue sin haber pull implícito — `sync=true` es opt-in y solo hace `git pull --ff-only` cuando el fast-forward es seguro (`behind > 0` y **no** `dirty` y **no** `ahead`); con trabajo sin commitear o commits sin pushear no toca el repo y explica por qué lo saltó. El re-indexado sí corre igual en esos casos: es solo lectura y refleja el trabajo en curso. `list_projects` incluye además `index_stale` calculado **sin red**, para que el aviso llegue en la llamada que ya se hace al entrar a un directorio. **Funciona en cualquier rama, no solo main/master**: se usa `repo.active_branch` y su `tracking_branch()`, así que un repo parado en `feature/x` se compara contra `origin/feature/x` (verificado en producción: hizo pull en `feature/orders` y en `develop`). El caso que sí queda fuera es una rama local **sin upstream**: no hay contra qué comparar y `behind`/`ahead` salen 0, lo que la haría pasar por "al día" — por eso `_inspect` propaga `comparable` y `_describe` lo reporta como "la rama no sigue a ninguna remota" sugiriendo `git push -u origin <rama>`, en vez de mentir.
- **Comparar `device_indexed_at` con la fecha de un commit exige normalizar timezones (`check_updates._as_aware`)**: `update_last_indexed` guarda `datetime.now().isoformat()` (NAIVE, hora local del equipo) y git devuelve `committed_datetime` AWARE con el offset del commit. Comparar los strings o los datetimes crudos da resultados falsos (y `TypeError` al comparar naive con aware). `astimezone()` sobre el naive lo interpreta como hora local, que es exactamente como se escribió, y deja ambos comparables como instantes.
- **En los modelos v4 el bloque `thinking` SALE DE `max_tokens` (`DEEPSEEK_MAX_TOKENS` 4096 → 8192, `_Unretryable`)**: distinto del gotcha de leer `content[0].text`. Si el razonamiento agota el presupuesto, la respuesta llega SIN bloque de texto (`content == ['thinking']`, `stop_reason == "max_tokens"`) y cae al `_raw_fallback`: esa categoría del audit sale con 0 tokens y sin hallazgos, **indistinguible de "todo limpio"**. Se descubrió con `describe_project` (5 secciones de prosa, no llegaba a escribir ni una), pero al arreglar el mensaje se vio que **el audit ya venía degradándose igual**: en una corrida de 4 categorías, 3 lotes se perdieron enteros. Dos palancas, ambas necesarias: el default subió a 16384 **y** `AUDIT_BATCH_MAX_CHARS` bajó de 120K a 45K — cuanto más código lleva el lote, más largo es el razonamiento, así que lotes más chicos acotan el thinking en origen (y desde que van en paralelo, tener más lotes ya no cuesta tiempo). Medido en este repo con 4 categorías: antes 313s procesando 11.6K tokens; después 158s procesando 53.4K. También `DEEPSEEK_TIMEOUT` a 120s (más salida tarda más, y un timeout corto la corta a mitad y dispara reintentos), y `profile_context` pide su propio `PROFILE_MAX_TOKENS` (12000). El fallo es **determinista**, así que reintentarlo 3 veces con backoff solo tarda 2 minutos más en dar el mismo error: `_call` lanza `_Unretryable` y corta el bucle en el primer intento, con un mensaje que nombra la causa real en vez del engañoso "DeepSeek no disponible". Al añadir cualquier prompt que pida salida larga, darle su propio presupuesto.
- **Auto-actualizacion del propio server (`self_update.py`)**: con varios equipos corriendo su copia, un cambio subido desde la laptop no llegaba al de trabajo hasta que alguien se acordaba de hacer `git pull` a mano. Decisiones: (1) **el repo se resuelve por `__file__`** (`Path(__file__).resolve().parent.parent`), NO desde la BD — en un equipo nuevo el server puede no estar registrado como proyecto indexado, pero siempre sabe donde vive su propio codigo. (2) **Nunca se reinicia solo**: cambiar los `.py` en disco no afecta al proceso vivo (los modulos ya estan en memoria) y un proceso stdio que se mata a si mismo deja la sesion de Claude Code colgada; se actualiza y se pide reinicio explicito. (3) El aviso viaja en `list_projects` (la llamada que ya se hace al entrar a un proyecto) con el fetch cacheado `CHECK_TTL_SECONDS=6h`, mas un chequeo al arrancar que ademas deja el cache caliente; si el chequeo falla, `list_projects` responde igual. (4) `apply_update` **no pisa trabajo sin commitear**: si el repo esta dirty aborta antes del pull (mismo criterio que `check_updates(sync=true)`). (5) Reinstala dependencias solo si el diff `antes..despues` toco `requirements.txt`, y si el `pip` falla marca `ok: false` y avisa de NO reiniciar todavia — reiniciar con deps a medio instalar deja sin MCP justo cuando hace falta para diagnosticar. En esta laptop no hay systemd: Claude Code lanza el server como proceso stdio, asi que "reiniciar el server" es reiniciar Claude Code.
- **El precio de DeepSeek depende de la HORA (`_rates()`, `DEEPSEEK_PEAK_HOURS_UTC`)**: desde el 2026-08-16 hay tarifa peak (01:00-04:00 y 06:00-10:00 UTC) que cuesta el DOBLE que off-peak. Los precios estaban hardcodeados como constantes de módulo (`COST_INPUT_PER_TOKEN = 0.14/1M`), así que tras el cambio de tarifas todo el registro de costos habría quedado ~40% por debajo del real sin que nada fallara. Ahora las cuatro tarifas y los rangos peak son env vars y `_rates()` elige según la hora UTC de la llamada. En hora de Ecuador (UTC-5) el peak cae en 20:00-23:00 y 01:00-05:00: **trabajando de día siempre es off-peak**. Un rango mal escrito en la env var se ignora con un warning en vez de tumbar el server — equivocarse en una variable de precios no debe impedir responder queries. Palanca grande pendiente: el *cache hit* cuesta $0.007/1M (30x menos que el miss) y el audit repite el mismo bloque de instrucciones en cada lote.
- **`CLAUDE.md` bloqueado explica un `files_indexed: 0` sorprendente**: esta en `BLOCKED_FILENAMES`, asi que editarlo NUNCA dispara re-indexado. Sospecha real levantada como bug del delta indexing ("edite CLAUDE.md y el incremental devolvio 0") — era esto, no un fallo de hashes. Para probar el incremental hay que tocar un archivo indexable (`.py`, `.md` que no sea CLAUDE.md, etc.). `index_project` devuelve ademas `skipped_unchanged` para que un `0` sea legible sin auditar el codigo.

- **Rutas por dispositivo (multi-equipo, misma Postgres) (`projects.device_paths`, `DEVICE_ID`)**: varios equipos comparten la misma base en Railway pero tienen los repos en rutas distintas; `projects.path` (unico) hacia que el path registrado por un equipo no existiera en el otro (caso real: `list_projects` en el equipo A devolvia rutas `/home/mickaell/Escritorio/...` del equipo B, y `index_project` fallaba con "la ruta ya no existe"). Solucion: columna `device_paths JSONB` = `{device_id: path}`; `path` queda como fallback legacy. Cada equipo define `DEVICE_ID` en su `.env` (fallback al hostname). `db.resolve_project_path(project, DEVICE_ID)` devuelve la ruta de este equipo con fallback al legacy. Invariantes: (1) **solo `index_project`/`register`/`clone`/`list` resuelven por dispositivo** — las queries (`query_context`/`find_usages`/`audit_project`/`get_file`) no leen del disco; su gate `is_path_allowed` pasa porque la whitelist (`load_project_paths`) carga el union de `path` legacy + TODOS los `device_paths`. **OJO**: que el gate pase NO significa que respondan desde cualquier equipo — leen de Chroma, que es local (ver el bullet de estado de indexado por dispositivo). La unica que sirve de verdad cross-equipo es `find_usages`, que lee `file_imports` de Postgres. (2) **`register_project` sobre un proyecto ya existente NO pisa el registro** (antes `insert_project` con `ON CONFLICT DO UPDATE SET path` clobbereaba la ruta del otro equipo): solo hace `set_device_path` para ESTE dispositivo. (3) **Migracion y adopcion al arrancar** (`main.py`): `ensure_device_paths_schema()` (`ADD COLUMN IF NOT EXISTS`, idempotente en la DB compartida) + `claim_local_paths(DEVICE_ID)` que adopta para este equipo las rutas legacy que existan en SU disco (nunca reclama rutas ajenas: chequea `os.path.isdir`). (4) `list_projects` devuelve la ruta de este dispositivo + `on_this_device`; si es `false`, el proyecto esta registrado en otro equipo y hay que `register_project` con su ruta local aca.

- **Estado de indexado por dispositivo (`indexed_files.device_id`, `projects.device_indexed_at`)**: los vectores viven en un ChromaDB **local a cada equipo**, pero `indexed_files` vive en la Postgres **compartida**. Con los hashes globales, el delta indexing leia el trabajo de OTRA maquina: cuando `openclaw` indexaba, `laptop` veia los hashes al dia y `index_project(incremental=True)` respondia `skipped_unchanged: 40` sin tocar su Chroma — que estaba vacio o con codigo viejo. Caso real (2026-07-26): de 16 proyectos, **12 tenian 0 chunks** en el Chroma de la laptop pese a figurar "indexados hace una hora", y `mcp-context-server` servia el `config.py` anterior al fix de `DEEPSEEK_MODEL` mas citas `archivo:linea` desviadas (chunks de una version vieja del archivo). El fallo era **mudo**: `query_context` devolvia `{"context": "", "tokens_used": 0}`, indistinguible de "no hay match", y el incremental nunca reparaba. Diseño: (1) los hashes se filtran por `device_id` **estricto** en `get_file_hashes`, asi que las filas legacy (`device_id NULL`) no cuentan como indice de nadie y el primer incremental de cada equipo se comporta como un full — **auto-reparacion**, sin migracion de datos ni comando nuevo. (2) `log_indexed_files` borra solo las filas de ESTE device (antes hacia `DELETE WHERE project_id` a secas, con lo que cada equipo pisaba los hashes del otro). (3) Las lecturas estructurales del audit (`get_files_by_path_patterns`, `get_file_extensions`) son **tolerantes** (`device_id = %s OR IS NULL`): describen que archivos tiene el repo, no el estado del Chroma, y un dato viejo ahi es mejor que ninguno. (4) `device_indexed_at` (JSONB, mismo patron que `device_paths`) alimenta `indexed_here` en `list_projects`, porque `last_indexed_at` global mostraba como reciente el indexado de otra maquina. (5) `query_context` avisa con `warning` cuando el proyecto no tiene NINGUN chunk local (`retriever.projects_without_chunks`) en vez de devolver contexto vacio. **Al desplegar esto hay que actualizar el codigo en TODOS los equipos**: un server con la version vieja sigue haciendo el `DELETE` global y vuelve a borrar los hashes de los demas. Regresion en `tests/test_device_index.py` (opt-in con `MCP_TEST_DATABASE_URL`, la suite normal es offline).
- **El arranque no puede bloquear el handshake MCP (`_db_ready`, tasks de fondo en `main.py`)**: `ensure_schema` + `claim_local_paths` + `load_project_paths` son round-trips reales a la Postgres de Railway (~1.4s por conexion, ~6s en total) y el import de `sentence_transformers` arrastra torch (~11s). Todo eso corria ANTES de `stdio_server()`, asi que el proceso no llegaba a leer stdin hasta terminar y Claude Code lo daba por caido sin reintentar (se vio en Windows 11). Ahora: la init de DB corre como task de fondo detras de un `asyncio.Event` (`_db_ready`) que `call_tool` espera, `self_update.check()` va en otra task, y el import de embeddings es perezoso dentro de `_get_model()`. Medido: import de `main` 0.8s, handshake completo 0.8s (antes ~15s). Invariantes: (1) `_db_ready.set()` va en un `finally` — un tool call esperando para siempre es peor que uno que falla con el error real; verificado E2E con la DB caida: el handshake responde igual y `call_tool` devuelve el `OperationalError` al instante. (2) Si la init falla, la whitelist queda VACIA y no se reintenta: el server queda utilizable solo tras reiniciar Claude Code (aceptado: con Postgres caida no funciona nada igual). (3) Las tasks se guardan en una lista: el loop solo mantiene referencias debiles y una task de fondo sin referencia fuerte puede recolectarse a medias.
- **`RAW_FALLBACK_MARKER` + `llm_available: false`**: cuando DeepSeek no responde, `_raw_fallback` devuelve chunks crudos con `(texto, 0, 0, 0.0)`, y eso se veia como un audit limpio o un `query_context` normal — el modo de fallo mudo que ya paso desapercibido semanas. El texto del fallback empieza por la constante `RAW_FALLBACK_MARKER`; `audit_project` y `query_context` la buscan en la respuesta y marcan `llm_available: false` con un `warning` que dice explicitamente que la ausencia de hallazgos NO significa codigo limpio. El acoplamiento (tools buscando un prefijo de texto) esta cubierto por `test_raw_fallback_lleva_el_marcador_que_buscan_las_tools`: sin el, reescribir el mensaje del fallback apagaria el aviso en silencio.
- **`DEEPSEEK_MAX_TOKENS` 16384 → 32768**: 16384 seguia sin alcanzar. Medido el 2026-08-20 en ESTE repo: `audit_project(categories=["correctness"])` agotaba el presupuesto en el bloque `thinking` y devolvia `content == ['thinking']`, o sea la categoria entera con 0 tokens y sin hallazgos. Con 32768 la misma corrida gasta 18-31K tokens y reporta los bugs sembrados. El techo no se paga si no se usa (se factura la salida real), asi que subirlo es gratis salvo cuando el modelo razona de mas.


## Variables de entorno necesarias

Ver `.env.example`. Las criticas son:
- `DEEPSEEK_API_KEY` — API de DeepSeek
- `GITHUB_TOKEN` — para repos privados (scope: repo)
- `DATABASE_URL` — PostgreSQL en Railway
- `PROJECTS_BASE_PATH` — directorio base donde viven los proyectos clonados
- `CHROMA_PERSIST_PATH` — donde ChromaDB guarda los vectores en disco
- `DEEPSEEK_MODEL` — modelo DeepSeek, default `deepseek-v4-flash` (ver gotcha abajo)
- `DEEPSEEK_TIMEOUT` — timeout (segundos) del cliente DeepSeek, default 60.0
- `DEVICE_ID` — identificador de este equipo para las rutas por dispositivo (fallback al hostname)

Opcionales con default (ver `.env.example`): `EMBEDDING_MODEL`, `AUDIT_TOP_K`, `AUDIT_BATCH_MAX_CHARS`, `AUDIT_MAX_CHUNKS`, `AUDIT_RAW_MAX_CHARS`, `AUDIT_VERIFY_ENABLED`, `AUDIT_CONCURRENCY`, `PROFILE_MAX_TOKENS`, `MAX_DISTANCE`, `RERANK_ENABLED`, `RERANK_CANDIDATE_MULT`, `RERANK_W_SEM`, `RERANK_W_LEX`.

## Tests y evaluación

- **Capa 1 (`tests/test_retrieval_recall.py`)**: recall de retrieval, determinista y gratis (sin DeepSeek/Postgres). Indexa `tests/fixtures/` en Chroma efímero y verifica que el archivo de cada bug sembrado se recupere. CI-able; se salta sin `sentence-transformers`.
- **Capa 2 (`eval/run_eval.py`)**: recall end-to-end del audit, no-determinista (~centavos). Registra las fixtures, corre el audit completo y puntúa cuántos bugs reporta + cuántos `must_not_flag` respeta (falsos positivos). Correr a mano al afinar prompts/modelo. NO en CI.
- **Golden set (`tests/fixtures/expected.json`)**: bugs sembrados a propósito (la única forma de tener ground truth) + `must_not_flag` (código legítimo que no debe reportarse, p. ej. el lock y la validación de input en `fake_backend/notificaciones.py`). Al añadir features al audit, sembrar un caso nuevo aquí; si la feature tiene riesgo de falso positivo, sembrar también su `must_not_flag`.
- **Tests con Postgres real (opt-in)**: la suite es offline por diseño (`conftest.py` inyecta env vars dummy). `tests/test_device_index.py` verifica SQL de verdad contra la base compartida y por eso solo corre con `MCP_TEST_DATABASE_URL` exportada; crea y borra su propio proyecto descartable. Mismo patrón para cualquier test futuro que necesite la DB.
- **`tests/test_audit_parallel.py`**: paralelismo del audit con `_call` monkeypatcheado — verifica que los lotes se re-agrupan por categoría EN ORDEN, que los tokens se suman y que corren en más de un hilo. Offline.
- **`tests/test_check_updates.py`**: crea repos git temporales de verdad (sin remoto) para el cálculo de `index_stale`, y verifica el guardarrail del `sync` (no hace pull sobre repos `dirty`/`ahead`, sí re-indexa). Offline.
- **`tests/test_startup_gating.py`**: regresion del arranque no bloqueante — `call_tool` no avanza hasta que `_db_ready` esta seteado. Usa un nombre de tool inexistente a proposito (responde `Tool desconocido` sin tocar Postgres), asi mide el gate y no la latencia de una conexion fallida. Offline.
- **`tests/test_describe_project.py`**: solo los extractores deterministas (paleta, manifiestos, estructura, naming, exclusión de fixtures). La síntesis DeepSeek no se testea. Offline.
- pytest ya está en `requirements.txt`; si el `.venv` local no lo tiene, sincronizar con `./.venv/bin/pip install -r requirements.txt`.

## Seguridad

- Archivos bloqueados: `.env`, `.pem`, `.key`, `.cert`, `secrets.json`, `credentials.json`, `serviceAccount.json`, `CLAUDE.md`, y lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `Pipfile.lock`, `composer.lock`, `Gemfile.lock`, `Cargo.lock`, `npm-shrinkwrap.json`)
- Sufijos bloqueados (generados/minificados): `.min.js`, `.min.css`, `.bundle.js`, `.map`
- Directorios bloqueados: `.git`, `node_modules`, `__pycache__`, `.venv`, `venv`, `.next`, `dist`, `build`, `.pytest_cache`
- Extensiones permitidas: `.py .js .ts .jsx .tsx .java .cs .go .rs .dart .kt .swift .rb .php .c .h .cpp .cc .cxx .hpp .html .css .scss .sass .md .txt .json .yaml .yml .sql .sh .bash`
- El servidor solo ejecuta git (via GitPython): `clone`/`pull` en `clone_project`, `fetch` en el chequeo de drift, `pull --ff-only` en `check_updates(sync=true)` y en la auto-actualizacion, y `ls-files` (solo lectura) para respetar `.gitignore` al indexar.
- **Unica excepcion a "solo git"**: `self_update._install_deps()` ejecuta `pip install -r requirements.txt` con `sys.executable` (el interprete del propio venv). Ocurre SOLO bajo `check_server_version(update=true)` y SOLO si el commit descargado toco `requirements.txt`. Es deliberado: sin eso, una actualizacion que agrega una dependencia deja el server roto al siguiente arranque, y el usuario descubre el fallo cuando ya no tiene MCP para diagnosticarlo. Ningun otro comando del sistema.
